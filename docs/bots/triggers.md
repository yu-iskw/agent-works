# Bot triggers

With `AW_BOT_WORKFLOWS=on` the teamwork runtime applies migration 0034 with the other bot migrations, runs `tick()` on a non-overlapping loop every `AW_BOT_TRIGGER_TICK_MS` (default 60000 ms), and routes `POST /v1/teamwork/bot-events` to `handleBotEventRequest` before member session authentication. Signing keys come from `AW_BOT_EVENT_KEYS` (one active key per source; see [operator-handoff.md](operator-handoff.md)).

The request body is the JSON encoding of `SignedEvent`, with `body` represented by Node's `{ "type": "Buffer", "data": [...] }` form. The signed `triggerId` is the event type. The handler accepts payloads up to 16 KiB and authenticated events from the previous 300 seconds, including the boundary. Event payloads are untrusted data and do not convey authority. One run starts per bot whose active revision declares a matching `event` trigger; a repeated delivery of the same `source` and `eventId` returns `duplicate`.

The scheduler uses the existing scheduling module's UTC slot evaluation in the declared IANA timezone. A local time skipped by spring daylight saving does not fire. A repeated local time in autumn maps to two distinct UTC slots and can fire twice. The existing cron scan looks back at most 366 days. `skip` suppresses slots at least a minute old; `run_once` chooses the latest slot since the cursor. A new revision starts at its publish time. Deferred slots remain pending until the next scheduled slot has passed, after which the capacity miss is audited. Each successful start is deduplicated by its trigger reference, and every schedule and event start carries the matched revision, so a publish in between is refused as `revision_changed` rather than running the newer revision.
