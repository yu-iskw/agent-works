# Contract ownership: `packages/domain` exports

Issue #170. This inventory says which `@agent-works/domain` exports are domain contracts that stay, and which are HTTP transport shapes that belong in `@agent-works/api-contract`. It follows the dependency rule in [ADR 0004](../adr/0004-application-core-and-adapter-boundaries.md). Domain stays free of transport. `api-contract` may depend on domain. Domain never imports `api-contract`; the architecture fitness test from #171 enforces that.

Consumers were found by scanning imports across the workspace on 2026-11-24 (`apps/*`, `packages/*`, `agents/skills`, `e2e`, `tools`, `scripts`, `evals`).

## Status of the moves

No export moved in #170. The capped scope allowed moving only clear transport-only shapes, and the two candidates (`askRequestSchema` and `IAP_ASSERTION_HEADER`) cannot move without a dependency change:

- `apps/api` and `apps/web` consume them, and neither depends on `@agent-works/api-contract`. Importing from it means adding `workspace:*` dependencies and updating `pnpm-lock.yaml`.
- `askRequestSchema` is a Zod schema. `api-contract` has no `zod` dependency. It validates with JSON Schema generated from `openapi.json`.
- `scripts/schema-source.mjs` runs before `tsc` in the `api-contract` build, so a schema owned by `api-contract` source would need a build-order or loader change before the generator can read it.

`openapi.json` and `operations.json` stay byte-identical. The follow-ups below list what each move needs.

## Deferred: mixed or unclear

| Export                                                                | Why it is not a clear move                                                                                                                                    |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `suspension-api` (`suspensionAuditSchema`, snapshot, history, result) | The API returns these, and the suspension ledger also persists the audit shape                                                                                |
| `schedule-fixtures`                                                   | Test fixtures exported from the domain index and used by api, web and api-contract. They belong in `@agent-works/fakes`, not in a production contract package |
| `workspace-tools`, `data-governance`                                  | Each mixes request/response schemas with domain rules used by the agent runtime and policy                                                                    |
| `./bot-definition`, `./bot-run` subpath exports                       | No consumer imports these subpaths. Consumers use the root `export *` instead                                                                                 |

## Follow-ups

1. Add `@agent-works/api-contract` as a `workspace:*` dependency of `apps/api` and `apps/web`, and decide whether `api-contract` takes `zod` or exposes JSON Schema validators only. This changes `pnpm-lock.yaml`, so it needs its own approval.
2. Move `IAP_ASSERTION_HEADER` to `api-contract` and use it in `src/transport.ts` and `scripts/spec.mjs`, replacing the duplicated literal.
3. Move the `ask` transport shapes. Give the ask use case a domain input type, and map `AskRequest` to it in `routes/ask.ts`. Make `schema-source.mjs` read the schema before `tsc` runs. Regenerate `openapi.json`: the `x-route-fingerprints` entry for every edited route file changes.
4. Move `schedule-fixtures` to `@agent-works/fakes`.
5. Split `suspension-api` into a persisted audit shape (domain) and response shapes (`api-contract`).
