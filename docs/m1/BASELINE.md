Limits at the baseline, all of which M1 changes: one-shot tasks, no follow-ups, serial execution, fixture Workspace only, fake identity only, one approval per task, no teammates, skills, catalog, inbox, plans or revisions, and a single backend.

Sandbox constraints that shape the work (from `docs/p0/PROGRESS.md`, re-observed): files matching `**/credentials*` cannot be read from the agent shell, so new files avoid that name. Host port binding is denied, so Playwright runs in Compose. The docker CLI cannot send a build context, so images never `COPY` the repo. The host shell exports `GOOGLE_CLOUD_LOCATION=us-central1`, so Compose uses `AW_M1_*` names.

## Reuse decisions

There is **one task system and one approval system**: the workbench tables, extended. M1 does not add a third task store next to legacy `0006_tasks` and `wb_tasks`.

| Concern       | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tasks         | `wb_tasks` gains `kind` (`flagship` for P0 rows, `teamwork` for M1), `workflow`, `conversation_id` and `result_owner`. P0's claim query filters `kind = 'flagship'`, so the P0 worker never touches M1 tasks. Teamwork tasks get their own transition table in `packages/domain/src/teamwork.ts`, keyed by kind, and share the status column with an extended check constraint.                                                                                                                                                   |
| History       | `wb_events` stays the single ordered history per task. Assignment and plan events carry `assignment_id` and `plan_version` in `detail`. Conversation messages reference task events and cards by id instead of copying them.                                                                                                                                                                                                                                                                                                      |
| Approvals     | `wb_approvals` gains `subject` (`flagship_doc`, `plan`, `publish`) and `subject_ref` (plan version or artifact revision). The `unique(task_id)` constraint becomes a partial unique index for `flagship_doc`, and P0's `on conflict` clauses name that index. Plan approvals and publish approvals reuse the same digest, expiry and `decided_by` columns and the same transactional decide path.                                                                                                                                 |
| Actions       | `wb_actions` keeps the idempotency key and status model. `task_id` stops being the primary key, so a task can have more than one action. P0 rows keep `wb:<task>:<approval>` keys.                                                                                                                                                                                                                                                                                                                                                |
| Model ledger  | `wb_model_calls` stays the one budget ledger. It gains `assignment_id`, `purpose` (`plan`, `contribution`, `synthesis`, `revision`, `conversation`, `smoke`) and `segment`. Each segment database holds its own ledger with a per-segment cap of 300, so the total across both cannot exceed Yu's 600. Restarting cannot reset it because the rows are durable.                                                                                                                                                                   |
| Model adapter | `vertex.ts` and `model-port.ts` are reused unchanged in behavior. Add bounded transient retry (at most 1, counted as a separate ledger row) and model-version verification (returned `modelVersion` must equal the configured ID or the ID plus a documented `-NNN` or date suffix).                                                                                                                                                                                                                                              |
| Evidence      | Evidence rows move from per-task to per-assignment (`wb_evidence` gains `assignment_id`), with location (`passage`, `lines`, `cell`), source revision and freshness. The source-data envelope and HTML escaping are reused. Citation-ID validation is kept and extended with a deterministic claim-support check.                                                                                                                                                                                                                 |
| Identity      | Real Google OpenID Connect sign-in in `web`, with authorization code, PKCE, state, nonce, server-side sessions in `web`'s own Postgres, and verification through the existing Google JWKS helper. `web` then mints a 60-second member assertion per request, audience `segment:<id>`. Each segment API verifies it with the **existing** `auth/iap.ts` verifier configured with `web`'s JWKS, issuer and audience. The fake IAP remains for P0 and the deterministic M1 `local-test` profile, labelled, and can never satisfy M3. |
| Segments      | Two api services (`api-alpha`, `api-beta`), each with its own Postgres service, volume, token-encryption key, member allowlist, source allowlist and model budget. `web` routes only to a static registry of segment IDs to backend URLs, validated at start-up against an allowed-host list. Every page and request is under `/s/<segment>/`.                                                                                                                                                                                    |
| Connectors    | New direct adapters in `apps/api/src/teamwork/sources/` for Drive read, Docs publish, BigQuery named queries and GitHub read, each taking the caller's per-segment token, never ADC. The legacy connector broker's approval-binding and idempotency ideas are reused as code patterns. Its fakes are not used in the live path. Fixture source adapters exist only for failure-path tests and are labelled.                                                                                                                       |
| Web           | Keep SSR TSX, `h()`, CSRF, CSP and design tokens. Extend the shell with a segment switcher, Inbox, Teammates, Tasks, Catalog and Connections. Grow the progressive-enhancement script for polling regions, drafts per segment and the diff view. No framework rewrite.                                                                                                                                                                                                                                                            |
| Runtime       | New `compose.m1.yaml` (project `aw-m1`, port `127.0.0.1:8280`) that mirrors P0's builder, volume and ADC pattern. `compose.p0.yaml` and P0 scripts keep working.                                                                                                                                                                                                                                                                                                                                                                  |

## Data and route migration

- Migration `0018_teamwork.sql` is additive. New tables: `tw_templates`, `tw_template_versions`, `tw_skills`, `tw_skill_versions`, `tw_teammates`, `tw_teammate_skills`, `tw_conversations`, `tw_messages`, `tw_plans`, `tw_assignments`, `tw_artifact_revisions`, `tw_inbox`, `tw_connections`, `tw_oauth_states`, `tw_audit`. Altered: `wb_tasks`, `wb_approvals`, `wb_actions`, `wb_evidence` and `wb_model_calls` gain nullable or defaulted columns. Existing rows default to `kind = 'flagship'`, `subject = 'flagship_doc'`, and so on, so P0 data reads exactly as before.
- P0 routes (`/v1/workbench/*`) are unchanged. M1 routes live under `/v1/teamwork/*` on the segment APIs. Both share the service primitives (`lockTask`, `move`, `appendEvent`, `recordModelCall`, `ensureBudget`).
- The P0 Playwright suites stay as regressions against `compose.p0.yaml`.

## Shared model (data shape first)

```text
TemplateVersion  {templateId, version, name, role, instructions, skillRefs[], capabilityRequests[]}  (immutable)
SkillVersion     {skillId, version, name, applicability, inputs[], steps[], validation[], outputShape, missingData, approvalBoundary}  (immutable)
Teammate         {id, owner, segment, fromTemplate@version, name, instructions, skills[{skillId@version}], status}
Conversation     {id, teammateId, owner}  -> Message {id, role, text, taskRef?, cardRef?}
Task (wb_tasks)  {id, owner, kind=teamwork, workflow, mode: manual|coordinated, resultOwner, status, conversationId?}
Plan             {taskId, version, assignments[PlannedAssignment], digest, state: proposed|approved|rejected|superseded}
Assignment       {id, taskId, planVersion?, teammateId, teammate@snapshot, skills@snapshot, brief, inputs, capabilities, deadline, state, lease, attempt, output?}
ArtifactRevision {taskId, revision, parent?, content, evidenceIds[], sourcesUsed[], generation{model, responseId, plan@v, skills@v}, diffFromParent}
InboxItem        {id, owner, taskId, kind: question|plan_review|approval|completed|failed|uncertain, ref, state: open|resolved}
Approval         {subject: plan|publish, subjectRef: planVersion|revision, digest, expiresAt, state}
```

Effective capabilities = segment policy ∩ member entitlement ∩ teammate configuration ∩ task scope ∩ connected and authorized connectors, computed in one pure function in `packages/domain/src/teamwork-policy.ts`. Model output can never add a capability.
